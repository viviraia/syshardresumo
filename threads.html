Threads (pthreads) e Mutex

Como dividir o trabalho em partes que executam ao mesmo tempo dentro de um processo, passar argumentos, devolver resultados e proteger dados compartilhados.

Programação concorrente: por quê e o que é difícil

Programação concorrente é dividir um programa em várias tarefas que envolvem:

  • compartilhamento de recursos: as tarefas usam os mesmos dados (ex.: venda de ingressos limitados, onde não se pode vender o mesmo ingresso duas vezes);
  • sincronização: algumas tarefas dependem de outras (ex.: contar pessoas em várias fotos é independente por foto, mas a resposta final só sai quando todas acabarem).

O desafio é que muita coisa acontece ao mesmo tempo e não dá para saber quem acontece primeiro.

ProcessosThreads

A troca de contexto funciona igual nos dois casos, e as threads também são escalonadas pelo kernel: não controlamos a ordem em que elas rodam.

CPU-bound são tarefas limitadas pela CPU: rodam tão rápido quanto ela permite, fazem pouca E/S e se dividem em partes independentes com pouca sincronização (fork-join). IO-bound passam o tempo esperando disco ou rede, e threads ajudam a sobrepor essas esperas.

API pthreads: create e join

#include <pthread.h>
// compile SEMPRE com -pthread:  gcc prog.c -o prog -pthread

int pthread_create(pthread_t *tid,              // onde guardar o ID da nova thread
                   const pthread_attr_t *attr,  // NULL = opções padrão
                   void *(*func)(void *),       // função a executar
                   void *arg);                  // argumento passado para func
int pthread_join(pthread_t tid, void **retval); // espera tid acabar (retval pode ser NULL)

// Toda função de thread tem ESTA assinatura:
void *minha_thread(void *arg) {
    printf("Hello thread!\n");
    return NULL;
}

pthread_t tid;
pthread_create(&tid, NULL, minha_thread, NULL);
pthread_join(tid, NULL);       // sincronização mais simples: espera o fim
Sem join, a thread pode nem rodar

Se o main chega ao return 0, o processo inteiro acaba e leva todas as threads junto. Sempre faça pthread_join em todas antes de sair. A ordem dos prints de várias threads muda a cada execução.

Duas threads não podem fazer join na mesma thread: o resultado é indefinido (man 3 pthread_join).

void * é um endereço de memória sem tipo. Ele diz onde estão os dados, mas não o que são. Dentro da thread, faça o cast para o tipo certo.

Passando argumentos (sempre no heap!)

void *tarefa_print_i(void *arg) {
    int *i = (int *) arg;          // reinterpreta o endereço como int*
    printf("%d\n", *i);
    return NULL;
}

int main() {
    int *vi = malloc(sizeof(int) * 4);
    pthread_t *tids = malloc(sizeof(pthread_t) * 4);
    for (int i = 0; i < 4; i++) {
        vi[i] = i;
        pthread_create(&tids[i], NULL, tarefa_print_i, &vi[i]);   // cada thread: SEU endereço
    }
    for (int i = 0; i < 4; i++) pthread_join(tids[i], NULL);
    free(vi);
    free(tids);
}
Os dois bugs clássicos de escopo
  1. Passar &i do laço: todas as threads recebem o mesmo endereço, e o main continua alterando i. Quando a thread lê, o valor já mudou (podem sair "4 4 4 4" ou "1 3 3 4").
  2. Passar o endereço de uma variável local de uma função que já retornou (ex.: criar_threads retorna os tids, mas as threads leem o i local dela). A pilha daquela função foi liberada ou reutilizada, e a thread lê lixo.

A solução é cada thread receber um bloco próprio, alocado com malloc, que vive até o fim (depois do join) e só então recebe free.

Vários argumentos e retorno: struct

typedef struct {
    int a, b;       // entradas
    int res;        // saída: a thread preenche
} t_arg;

void *multiplica(void *_arg) {
    t_arg *arg = _arg;             // cast implícito de void* em C
    arg->res = arg->a * arg->b;
    return NULL;
}

int main() {
    int n = 4;
    pthread_t *tids = malloc(sizeof(pthread_t) * n);
    t_arg **args = malloc(sizeof(t_arg *) * n);
    for (int i = 0; i < n; i++) {
        args[i] = malloc(sizeof(t_arg));
        args[i]->a = i;
        args[i]->b = 10;
        pthread_create(&tids[i], NULL, multiplica, args[i]);
    }
    for (int i = 0; i < n; i++) {
        pthread_join(tids[i], NULL);
        printf("%d * %d = %d\n", args[i]->a, args[i]->b, args[i]->res);  // lê o resultado DEPOIS do join
        free(args[i]);
    }
    free(args);
    free(tids);
    return 0;
}

Retornar pela struct equivale a uma função que "retorna" escrevendo num ponteiro recebido. Também dá para retornar via return ptr; e pegar no pthread_join(tid, &ret), mas o padrão da disciplina é o campo na struct.

Race condition e região crítica

Definições

Race condition: a saída do programa depende da ordem de execução das threads. Em geral ocorre quando uma variável é usada por mais de uma thread e há pelo menos uma escrita, ou quando várias threads trabalham no mesmo arquivo.

Região crítica: parte do programa que só pode ser executada por uma thread por vez. Elimina a race, mas também a concorrência ali, e pode virar gargalo.

Por que soma = soma + v[i] dá errado com várias threads? Porque são três passos (ler soma para um registrador, somar, escrever de volta). Entre o ler e o escrever, outra thread pode atualizar a soma, e uma das atualizações se perde. O resultado fica menor que o esperado e muda a cada execução.

Mutex (exclusão mútua)

  • lock: se estiver destravado, trava e continua; se não, espera até alguém destravar.
  • unlock: se você tem a trava, destrava e permite que outra thread trave.
  • Não há garantia de ordem: qualquer thread que espera pode pegar a trava (em tese, uma pode esperar "para sempre").
#include <pthread.h>
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;   // cria e inicializa (ou pthread_mutex_init(&m, NULL))

pthread_mutex_lock(&mutex);
soma = soma + spa->vetor[i];        // REGIÃO CRÍTICA: só o mínimo necessário
pthread_mutex_unlock(&mutex);

pthread_mutex_destroy(&mutex);      // no fim (se usou pthread_mutex_init)

Crie o mutex no main, antes de criar as threads, e passe o endereço dele pela struct de argumentos (ou declare-o global).

Mutex é caro: como economizar

Com lock/unlock a cada iteração, o programa fica correto, porém mais lento que a versão errada: perde-se o paralelismo e as operações de lock/unlock são custosas (meça com time). Há duas otimizações, e a segunda é a melhor:

struct soma_parcial_args {
    double *vetor;
    int start, end;            // intervalo [start, end)
    pthread_mutex_t *mutex;    // usado na versão 1
    double resultado;          // usado na versão 2
};
double soma_total = 0;

// 1) acumulador LOCAL por thread; um único lock no fim
void *soma_parcial(void *_arg) {
    struct soma_parcial_args *spa = _arg;
    double local = 0;
    for (int i = spa->start; i < spa->end; i++) local += spa->vetor[i];
    pthread_mutex_lock(spa->mutex);
    soma_total += local;               // 1 lock por thread, não por elemento
    pthread_mutex_unlock(spa->mutex);
    return NULL;
}

// 2) SEM mutex: cada thread devolve sua parcial na struct; o main soma após o join
void *soma_parcial2(void *_arg) {
    struct soma_parcial_args *spa = _arg;
    spa->resultado = 0;
    for (int i = spa->start; i < spa->end; i++) spa->resultado += spa->vetor[i];
    return NULL;
}
// main:  for (...) { pthread_join(tids[i], NULL); total += args[i]->resultado; }  // sequencial: sem race

Dividir o vetor: para N elementos e T threads, a thread k recebe start = k*N/T e end = (k+1)*N/T. Para o vetor todo, start = 0 e end = n; para a primeira metade, start = 0 e end = n/2.

valgrind e memória (costuma valer pontos)

gcc -g q4.c -o q4 -pthread
valgrind --leak-check=full ./q4 2 arquivo.txt
# objetivo: "All heap blocks were freed" e "ERROR SUMMARY: 0 errors"
  • Todo malloc e realloc precisa de um free: as structs de argumento, as strings lidas, o vetor de tids e o vetor de ponteiros.
  • Faça os free depois do pthread_join, senão a thread pode acessar memória já liberada.
  • Feche os fds e destrua os semáforos/mutex inicializados.
  • "Invalid read" geralmente significa ler além do fim de um buffer (faltou espaço para o '\0').

Resumo relâmpago

  • A função da thread é void *f(void *arg); crie com pthread_create(&tid, NULL, f, arg) e espere com pthread_join(tid, NULL).
  • Compile com -pthread.
  • Cada thread recebe o seu próprio argumento no heap (struct). O resultado volta num campo da struct, lido depois do join.
  • Variável compartilhada com escrita é race condition: proteja com pthread_mutex_lock/unlock, e só na região crítica.
  • Mutex é caro: prefira acumuladores locais ou parciais devolvidas ao main.
  • Manuais: man 7 pthreads, man 3 pthread_create, man 3 pthread_join, man pthread_mutex_lock (pacote manpages-posix-dev).
