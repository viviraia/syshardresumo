Processos: fork, wait, exec

Como o Sistema Operacional cria, isola, espera e substitui programas em execução. É a base das questões de "integrar com outro executável" da Prova Final.

Sistema Operacional, kernel e POSIX

O Sistema Operacional permite que um usuário execute vários programas de maneira "simultânea" e segura. Ele controla o acesso à memória, ao armazenamento e aos dispositivos, garantindo isolamento, divisão do tempo de CPU e acesso concorrente aos dispositivos.

ConceitoO que é
KernelSoftware do sistema que gerencia programas, memória e recursos de hardware. Roda com privilégios totais (anel 0 no x86). Grosso modo, é um conjunto de handlers de interrupção.
Processo de usuárioQualquer programa em execução. Roda com privilégios limitados (anel 3). A falha de um processo não afeta os outros. Para acessar hardware (memória, disco, rede, outros processos) faz chamadas de sistema ao kernel.
SyscallPedido de um processo ao kernel (fork, read, open, kill...).
InterrupçãoAviso do hardware ao kernel (disco terminou, pacote de rede, timer, teclado).
SinalAviso do kernel a um processo ("exceção de software"). Ver Sinais.
POSIXFamília de padrões IEEE que define a API do SO (usuários e grupos, arquivos e permissões, processos, comunicação entre processos, acesso a drivers). Linux e macOS são POSIX; código POSIX é compatível em nível de código-fonte. Cabeçalho principal: <unistd.h>. No Windows há a API própria (WINE traduz Windows→POSIX; Cygwin implementa POSIX sobre Windows).

Um sistema de computação combina hardware + SO, é de uso geral e reprogramável. Uma calculadora não é (sem armazenamento secundário, não é de uso geral); um microcontrolador também não (não tem SO).

Processo, contexto e troca de contexto

Um processo dá ao programa duas ilusões:

  • Fluxo de controle lógico: parece ter a CPU só para ele, graças à troca de contexto (context switch).
  • Espaço de endereçamento privado: parece ter a memória só para ele (Stack, Heap, Data, Code), graças à memória virtual.

Na realidade, os processos são intercalados. Numa troca de contexto o kernel:

  1. grava os registradores do processo atual na memória;
  2. escolhe o próximo processo (escalonador);
  3. carrega os registradores salvos dele e troca o espaço de endereçamento.

O contexto de execução é tudo o que precisa ser salvo e restaurado: registradores, memória e estado. Em processadores multicore cada core roda um processo, e o kernel decide qual roda em qual core.

Ciclo de vida

Um processo alterna entre rodando, pronto (esperando a CPU) e bloqueado (esperando E/S). Ele sai de "rodando" por:

  • fim do tempo limite de execução (preempção pelo timer), indo para pronto;
  • uma chamada de sistema que espera hardware (ex.: read), indo para bloqueado;
  • a interrupção do dispositivo que o devolve de bloqueado para pronto.

O fluxo de controle muda por saltos/call/ret (dentro do programa) e por exceções/interrupções/sinais (eventos do sistema: dados do disco, divisão por zero, Ctrl+C, timer).

fork: criando processos

#include <unistd.h>
#include <sys/types.h>

pid_t fork(void);      // cria um CLONE do processo atual
pid_t getpid(void);    // meu pid
pid_t getppid(void);   // pid do meu pai
Regra de ouro

fork retorna duas vezes:

  • no pai, retorna o pid do filho (> 0);
  • no filho, retorna 0;
  • em caso de erro, retorna -1.

Os dois continuam executando a partir da linha seguinte ao fork, cada um com sua própria cópia da memória: mudar uma variável num deles não muda no outro.

pid_t pai, filho;
int variavel = 5;
filho = fork();
if (filho == 0) {
    // FILHO
    pai = getppid();
    filho = getpid();
    variavel *= 2;
    printf("filho %d, pai %d, variavel %d\n", filho, pai, variavel);   // 10
} else {
    // PAI
    pai = getpid();
    printf("pai %d, filho %d, variavel %d\n", pai, filho, variavel);   // 5
}
Pegadinhas
  • Memória separada: um while (rodando) no pai nunca termina se só o filho faz rodando = 0. Para esperar o filho, use wait.
  • Ordem de execução: não é possível saber quem roda primeiro (o escalonador decide). Isso muda só a ordem dos prints, não os valores.
  • Filho que continua o loop: num for que faz fork, o filho também continua o laço e cria "netos". Para N filhos diretos, o filho precisa sair (exit/return/break) dentro do if (pid == 0).
  • Buffer do printf: o buffer de stdout é copiado no fork. Um printf sem \n antes do fork pode aparecer duas vezes. Dê fflush(stdout) ou termine com \n.

Criar N filhos numerados (exercício da aula 11)

#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    int id = 0;                    // 0 = pai
    for (int i = 1; i <= 8; i++) {
        pid_t p = fork();
        if (p == 0) {              // filho: guarda seu id e SAI do laço
            id = i;
            break;
        }
    }
    if (id == 0) {
        printf("Eu sou o processo pai, pid=%d, meu id do programa é %d\n", getpid(), id);
        for (int i = 0; i < 8; i++) wait(NULL);   // espera os 8
    } else {
        printf("Eu sou um processo filho, pid=%d, ppid=%d, meu id do programa é %d\n",
               getpid(), getppid(), id);
    }
    return 0;
}

Contando processos em forks encadeados

Cada fork() executado por k processos gera mais k processos. Com n forks em sequência (sem if), o total é 2n processos, contando o original.

fork();          // 2 processos
fork();          // 4 processos
printf("oi\n");  // impresso 4 vezes

Com if, desenhe a árvore: em cada fork, um ramo "pai" (retorno > 0) e um ramo "filho" (retorno 0). Na questão de revisão da aula 20 (f1 = fork(); f2 = fork();) há 4 processos. Os valores (f1, f2) identificam quem é quem:

  • f1≠0, f2≠0: o original;
  • f1≠0, f2=0: o 2º filho do original;
  • f1=0, f2≠0: o 1º filho;
  • f1=0, f2=0: o neto.
Como julgar "essa saída é possível?"

Uma saída é impossível se viola uma relação de causa → efeito:

  • um processo imprime algo antes de existir (o filho só existe depois do fork do pai);
  • a ordem dos prints de um mesmo processo está trocada;
  • um pai que faz wait imprime "fim" antes do fim do filho;
  • os pids não batem com a árvore (o filho de 138 aparecendo como filho de 137, um pid de filho igual a 0 impresso pelo pai).

Prints de processos diferentes sem dependência podem vir em qualquer ordem. Explique por quê; não basta apontar a diferença para um teste.

wait e waitpid: esperando filhos

#include <sys/types.h>
#include <sys/wait.h>

pid_t wait(int *wstatus);                            // espera QUALQUER filho
pid_t waitpid(pid_t pid, int *wstatus, int options); // espera um filho específico
  • Bloqueiam até um filho terminar e retornam o pid de quem terminou (-1 se não há filhos).
  • O status de término vem em *wstatus (pode passar NULL se não interessar).
  • waitpid(pid, &st, 0) espera aquele filho. waitpid(-1, &st, 0) equivale a wait(&st).
  • waitpid(pid, &st, WNOHANG) não bloqueia: retorna 0 se o filho ainda está rodando e o pid se já terminou. Serve para "só mandar o sinal se o filho ainda estiver vivo".

Macros para ler o wstatus

MacroSignificado
WIFEXITED(st)Verdadeiro se o filho terminou normalmente (return do main ou exit).
WEXITSTATUS(st)O valor retornado pelo main (só os 8 bits menos significativos: 0..255). Use só se WIFEXITED.
WIFSIGNALED(st)Verdadeiro se o filho foi terminado por um sinal (Ctrl+C, SIGSEGV, divisão por zero, kill...).
WTERMSIG(st)Número do sinal que matou o filho. Use strsignal(sig) (<string.h>) para obter o nome legível.
int wst;
pid_t quem = wait(&wst);
if (WIFEXITED(wst)) {
    printf("%d terminou normal, retorno %d\n", quem, WEXITSTATUS(wst));
} else if (WIFSIGNALED(wst)) {
    printf("%d morreu pelo sinal %d (%s)\n", quem, WTERMSIG(wst), strsignal(WTERMSIG(wst)));
}
Pegadinha clássica: retorno negativo

Se o filho faz return -1, WEXITSTATUS devolve 255 (só 8 bits, sem sinal). Para recuperar o -1, faça o cast: int ret = (char) WEXITSTATUS(wst); (dica que apareceu no simulado oficial). Do mesmo jeito, return 256 vira 0.

Zumbi e órfão: um filho que terminou e ainda não foi esperado vira zumbi (a entrada dele continua na tabela de processos até o wait). Por isso o pai deve sempre esperar os filhos. Um filho cujo pai morreu vira órfão e é adotado pelo init/systemd (pid 1), e o getppid() dele muda.

Argumentos do programa: argc e argv

int main(int argc, char *argv[]) {
    for (int i = 0; i < argc; i++) printf("arg: %s\n", argv[i]);
}
// $ ./exemplo-args teste var bla foo
// argc = 5, argv = {"./exemplo-args", "teste", "var", "bla", "foo"}  (argv[argc] == NULL)
  • argv[0] é o nome do programa chamado. argc conta ele também.
  • Os argumentos são strings. Para converter, use atoi/atol (inteiro), atof (double) ou strtol (com detecção de erro). Um texto que não é número vira 0 com atoi/atof.
  • Valide argc logo no início e mostre a mensagem de uso ("USAGE: ...") se estiver errado.

exec: carregando outro programa

fork só cria clones. Para rodar outro programa usamos a família exec, que carrega o programa do disco no contexto do processo atual, substituindo-o por completo (código, dados, pilha). O pid continua o mesmo.

#include <unistd.h>
int execvp(const char *file, char *const argv[]);

char prog[] = "ls";
char *args[] = {"ls", "-l", "-a", NULL};   // começa com o nome, TERMINA com NULL
execvp(prog, args);
printf("Fim do exec!\n");   // SÓ executa se o execvp FALHAR
Regras do exec
  • Nunca retorna se der certo. Se retornar, deu erro (retorna -1): trate com perror("execvp"); exit(1);.
  • O vetor de argumentos vira o argv do novo main. {"prog1","arg1","arg2",NULL} gera argc = 3 (o NULL não conta).
  • execvp: o v indica vetor de argumentos e o p indica que o programa é procurado no PATH. Para um executável da pasta atual, use "./siscoin".
  • Variantes: execl/execlp (lista de argumentos), execv (sem PATH), execve (com variáveis de ambiente).
  • Na prova, não pode usar system(). O padrão é fork + exec + wait.

Padrão fork + exec + wait (com retry)

Este é o modelo da questão do SisCoin do simulado: chamar um executável repetidamente até ele dar certo.

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    if (argc != 4) { printf("USO: ./q2 <origem> <destino> <valor>\n"); return 1; }
    int ret;
    int wst;
    do {
        pid_t filho = fork();
        if (filho == 0) {
            char *args[] = {"./siscoin", argv[1], argv[2], argv[3], NULL};
            execvp(args[0], args);
            perror("execvp");          // só chega aqui se falhar
            exit(1);
        }
        waitpid(filho, &wst, 0);
        if (WIFEXITED(wst)) {
            ret = (char) WEXITSTATUS(wst);   // recupera -1
            printf("siscoin retornou %d\n", ret);
        } else {
            ret = 1;                          // morreu por sinal: tenta de novo
        }
    } while (ret > 0);   // 1..4 = falha de rede -> repete; 0 = ok; -1 = erro de parâmetro
    return 0;
}

Vários processos em paralelo (lab do web_downloader)

No Lab de Processos, o web_downloader baixa cada URL num processo separado. Os conceitos vão subindo:

  • C: lê as URLs com -f, faz um fork por URL e mostra "{url} baixada com sucesso!".
  • B: o pai espera todos e mantém no máximo N processos (-N, padrão 4), ou seja, no máximo N+1 contando o original.
  • A: mensagens sem embaralhar, Ctrl+C pergunta se quer sair (mata os filhos e apaga os arquivos parciais), mensagem quando o download falha.
// Limitar a N filhos simultâneos: conte os ativos; ao chegar em N, espere um terminar.
int ativos = 0;
for (int i = 0; i < n_urls; i++) {
    if (ativos == N) { wait(NULL); ativos--; }
    pid_t p = fork();
    if (p == 0) { baixa(urls[i]); exit(0); }
    ativos++;
}
while (ativos > 0) { wait(NULL); ativos--; }   // espera os que sobraram

O nome do arquivo de saída segue a regra do lab: ignora http:// e https:// e troca barras e pontos (exceto o último) por _. Assim, http://exemplo.com/pagina.html vira exemplo_com_pagina.html.

Resumo relâmpago

  • fork() retorna 0 no filho, o pid do filho no pai e -1 em erro. A memória é copiada, não compartilhada.
  • wait(&st) e waitpid(pid,&st,opt) bloqueiam e devolvem o pid. WNOHANG não bloqueia.
  • Para ler o status: WIFEXITED/WEXITSTATUS (cast (char) para negativos) e WIFSIGNALED/WTERMSIG (+ strsignal).
  • execvp(nome, args) com args[0] = nome e o último elemento NULL. Só retorna em erro.
  • Includes: <unistd.h>, <sys/types.h>, <sys/wait.h>, <stdlib.h>, <string.h>.
  • Consulte sempre: man 2 fork, man 2 wait, man 3 execvp, man 3 strsignal. If in doubt, then man!
